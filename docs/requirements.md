> **초안입니다. (2026-11-26 작성)**
> - 번호 `REQ-…`는 **임시 번호**입니다. 팀에서 쓰는 `RF-…`(기능 요구사항), `UC-…`(유스케이스) 번호가 PR #57과 앱 코드에 인용되어 있는데, 그 원본 문서는 이 저장소에 없습니다. 원본을 확인한 뒤 번호를 맞춥니다.

### 2.2 온도 표시와 센서 값 처리
| 번호 | 요구사항과 확인 기준 | 우선순위 | 상태 | 확인 |
| --- | --- | --- | --- | --- |
| REQ-TMP-01 | 장소의 온도는 **측정 후 지난 시간(분)** 과 함께 보여 준다. 앱은 화면을 열 때 서버에서 값을 받는다. | 필수 | 구현 | `test_spot_shows_latest_reading_with_age`, `SpotDisplayTest` |
| REQ-TMP-02 | 측정한 지 **30분 이상**인 값은 "최신 값이 아닐 수 있어요"로 구분해 보여 준다. | 필수 | 구현 | `test_stale_flag_follows_threshold`, `test_is_stale_boundary` |
| REQ-TMP-03 | 장소에 설치된 센서의 새 값을 먼저 쓴다. 없으면 **200m 안**의 새 값이 있는 가장 가까운 센서 값을 빌리고, 빌린 값이면 거리를 함께 보여 준다. | 필수 | 구현 | `test_dead_sensor_spot_borrows_the_nearest_fresh_sensor`, `test_sensors_beyond_the_max_distance_are_not_borrowed`, `test_stale_neighbors_are_not_borrowed` |
| REQ-TMP-04 | 보여 줄 값이 하나도 없으면 틀린 값을 만들지 않고 **"값을 받을 수 없어요"** 로 보여 준다. | 필수 | 구현 | `test_spot_without_value_has_no_source` |
| REQ-DATA-01 | 서버는 연구실 센서 값을 **60초마다** 가져온다. 요청 제한 시간은 **10초**이고, 측정한 지 **1시간 이내**인 값만 저장한다. | 필수 | 구현 | `test_sync_stores_fresh_registered_sensor_without_humidity`, `test_sync_skips_unusable_names_and_stale_rows` |
| REQ-DATA-02 | 같은 센서의 같은 측정 시각 값은 **한 번만** 저장한다. | 필수 | 구현 | `test_sync_is_idempotent_and_dedupes` |
| REQ-DATA-03 | 온도가 **-20~45℃ 밖**이거나, 습도가 0~100% 밖이거나, 온도와 습도가 모두 0.0인 값은 최신 값, 평균, 추천에 쓰지 않는다. | 필수 | 구현 | `test_is_valid_reading_rejects_out_of_range`, `test_all_zero_reading_is_stored_but_ignored_for_latest_and_average` |
| REQ-DATA-04 | BLE로 받은 값이 **5건 이상, 10분 이상** 같으면 고장 의심으로 표시하고, 앱은 그 온도를 보여 주지 않는다. | 필수 | 구현 | `test_long_fixed_run_is_flagged`, `HomeDisplayTest` |
| REQ-DATA-05 | 앱은 BLE로 읽은 값을 연구실 서버로 올린다. 같은 센서는 **10초에 한 번**만 올리고, 오류값은 올리지 않는다. 실패하면 **5초에서 최대 5분** 간격으로 다시 보낸다. | 필수 | 구현 | `UploadQueueTest`, `ReadingCheckTest`, `LabSensingApiTest` (10초 간격은 단위 테스트 없음) |

> 습도는 요구사항에 넣지 않았습니다. 연구실 API가 습도를 주지 않아 화면에는 온도만 표시합니다. (3장의 "기획과 달라진 점" 참고)

## 3. 비기능 요구사항

| 번호 | 요구사항과 확인 기준 | 상태 | 확인 |
| --- | --- | --- | --- |
| REQ-OFF-01 | 우리 서버에 접속하지 못해도 장소, 코스, 도착 판정, 방문 기록이 동작한다. 코스 목록은 **서버, 폰에 저장한 마지막 목록, 앱에 넣은 기본 목록** 순서로 쓰고, 저장본과 기본 목록에는 온도를 넣지 않는다. | 구현 | `TourDataTest`, `test_snapshot_has_no_temperatures`, 현장 |
| REQ-REL-01 | 연구실 서버에 접속하지 못해도 우리 서버는 멈추지 않고 저장된 마지막 값을 준다. 다음 주기(**60초**)에 다시 시도한다. | 구현 | `test_run_once_survives_lab_server_failure` |
| REQ-PRIV-01 | 우리 서버는 사용자의 위치, 방문 기록, 기기 ID를 **저장하지 않는다.** 방문 기록은 폰에 저장하고 앱은 서버로 보내지 않는다. 다만 **연구실 서버로 센서 값을 올릴 때는 업로드 형식의 `sender` 칸에 폰의 안드로이드 ID가 함께 간다.** (위치는 보내지 않음) 방문 기록이 휴대폰 백업에 포함되는 것은 아직 정하지 않았다. (설계 문서 10장) | 구현 | ERD(설계 문서 4장)에 사용자 관련 표가 없음 |
| REQ-PRIV-02 | 앱이 걷는 길을 받으려고 외부 경로 서비스에 보내는 현재 위치는 **소수점 4자리(약 11m)** 로 반올림한다. | 구현 | `TourRouteTest` |
| REQ-OPS-01 | 시연 전에 점검 도구 한 번으로 서버 상태, 센서 값, 한글, 장소 12곳의 온도, 코스를 **정상, 주의, 실패**로 확인할 수 있다. | 구현 | `test_the_real_tour_data_is_checked_end_to_end`, `test_main_reports_an_unreachable_server` |
| REQ-OPS-02 | 앱의 BLE 스캔과 자동 도착은 **앱 화면이 켜져 있는 동안** 동작한다. 백그라운드 동작은 범위에서 뺀다. | 구현 | `ScanLeaseTest`, 현장 |

### 기획과 달라진 점
Notion의 기획 페이지와 지금 구현이 다른 부분입니다. **발표한 프로포절 PPT와는 대조하지 않았습니다.**

| 기획 | 지금 | 이유 또는 근거 |
| --- | --- | --- |
| 실시간 온습도 표시 | 온도만 표시. 화면을 열 때 받고, 측정 후 지난 시간을 함께 표시 | 연구실 API에 습도가 없음 |
| Pi에 가까워지면 장소 소개 카드를 자동 표시 | 도착은 자동 기록. 카드는 카드 장소 6곳에서 표시 (구현 중) | #37 |
| 환경 맞춤 코스 추천이 핵심 기능 | 선택 기능 (구현은 완료) | #5 합의 |
| 방문 데이터를 쌓아 인기 장소 파악 가능 | 방문 기록을 서버로 모으지 않으므로 **파악할 수 없음** | 개인정보: 방문 기록은 폰에만 저장 |

## 4. 팀이 정해야 하는 정량 기준
아래는 **아직 정한 적도, 잰 적도 없는 기준**입니다. "제안 값"은 의논을 시작하기 위한 값이며, 정한 뒤에 위 표에 번호를 붙여 옮깁니다. 잴 수 없다면 요구사항에 넣지 않는 편이 낫습니다.

| 항목 | 제안 값 | 재는 방법 |
| --- | --- | --- |
| 자동 도착까지 걸리는 시간 | 센서 앞에 선 뒤 **15초 이내** | 통합 테스트에서 센서마다 5번씩 잼 |
| 자동 도착 성공률 | 센서마다 **5번 중 4번 이상** | 위와 같음 |
| 서버 응답 시간 (`GET /api/courses`) | 같은 Wi-Fi에서 **2초 이내** | 시연 노트북과 폰으로 잼 |
| 시연 전 서버 점검 | **실패 0개** | `python -m app.check_server` |
