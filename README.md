# CampusTourGuide

캠퍼스 BLE 투어 가이드 (오픈소스개발프로젝트 팀 프로젝트)

캠퍼스에 설치된 라즈베리파이 센서의 BLE 신호로 방문객의 위치를 인식하고, 장소 소개와 실시간 온도, 투어 코스를 안내하는 앱입니다.
이 저장소는 **백엔드(서버 및 DB)** 입니다.

## 프로젝트 소개

- **해결할 문제**: 방문객은 지도를 봐도 그 장소의 날씨를 모릅니다. 기상청 날씨는 캠퍼스 안의 장소별 차이를 반영하지 못하고, GPS는 건물이 밀집한 곳에서 오차가 큽니다.
- **핵심 기능**
  1. 위치 인식 장소 안내: Pi에 가까워지면 BLE로 장소를 인식하고 소개 카드를 표시
  2. 실시간 온도: 장소에서 가장 가까운 센서의 현재 온도와 측정 시각을 카드에 표시 (습도는 표시하지 않음. 연구실 API에 습도가 없음)
  3. 코스 및 소요 시간: 고정 코스 2~3개, 코스별 소요시간, 방문 자동 체크와 진행률
  4. 환경 맞춤 코스 추천: 너무 덥거나 추우면 짧은 코스 추천
  5. (선택) 지도 길안내, 영어 지원, 관리자 콘텐츠 편집
- 핵심 기능이 누적 데이터가 아니라 **현재 값**만으로 동작합니다. 서버 값은 오래됐을 수 있어 항상 "n분 전 측정"을 함께 표시합니다.

## 동작 구조

```
센서(Pi 5대)                         연구실 서버(수업 서버)                  우리 서버 (이 저장소)
온도 측정                            센서 데이터 수집·제공                     온도 저장·가공
 ├─ 센서가 직접 전송 ─────────────▶  GET /sensor/api/map  ◀──── 1분마다 ────  장소·코스 제공
 └─ BLE 광고 ─▶ 앱 ─ 업로드 ─────▶  (앱의 업로드도 여기로)                          │
                │                                                                  │
                └── 스캔 → RSSI로 "도착" 판정 → 장소 카드 + 온도 표시 ◀── HTTP ─────┘
```

- **센서 데이터는 연구실 서버에서 가져옵니다.** 서버가 연구실 공용 API(`/sensor/api/map`)에서 1분마다 센서 온도를 가져와 DB에 저장합니다. 센서가 직접 올리는 값과 앱이 올리는 값이 모두 이 API로 모입니다. 우리 오픈소스 센서 5대뿐 아니라 **연구실이 캠퍼스 곳곳에 설치한 센서(위치가 있는 것 모두)도 자동으로 등록**해서, 센서가 죽은 장소가 가까운 센서의 값을 빌려 쓸 수 있습니다. 연구실 서버가 응답하지 않아도 마지막으로 저장한 값을 보여줍니다.
- 연구실 API는 **온도(정수, 소수점 버림)와 CO2만** 주고 습도는 없습니다. 그래서 화면에는 온도만 표시합니다. 습도는 앱이 BLE로 읽어 우리 서버(`POST /api/readings`)로 올린 값이 있을 때만 저장됩니다.
- BLE 패킷은 13바이트(Little-Endian)입니다: 온도 x100(2) + 습도 x100(2) + AQI(1) + TVOC(2) + eCO2(2) + 시각(4). 센서ID는 들어 있지 않습니다.
- 장소는 캠퍼스 전체로 잡고, 장소의 온도는 **가장 가까운 센서 값**을 사용하는 방향입니다. (센서가 없는 장소의 도착 판정은 센서가 있는 곳은 BLE 자동, 없는 곳은 "도착" 버튼으로 정했습니다. #2)

## 팀 구성

| 역할 | 담당 |
| --- | --- |
| Pi, 센서, 테스트 | 유서진 |
| BLE, 네트워크 | 황지유 |
| 백엔드 (서버 및 DB) | 최세원(팀장) |
| 프론트엔드 (앱 UI 및 문서) | 홍유진 |

캠퍼스에 설치된 센서는 연구실 장비라 Pi 코드를 수정할 수 없습니다. 그래서 Pi, 센서 담당은 아래 테스트 업무를 맡습니다.

- 센서 상태 점검과 이상 발견 시 연구실 연락
- RSSI 현장 측정과 도착 판정 기준값 도출
- 센서 설치 위치의 좌표 측정
- 통합 테스트(Pi, 앱, 서버)와 현장 리허설
- 테스트 결과 문서화

## 센서

### 오픈소스 센서 5대 (`kind`: `opensrc`)

수업에서 제공된 센서입니다. 앱 화면과 문서에서 "센서 N"은 BLE 이름이 `opensrcN`인 센서를 뜻하고, 서버의 `sensor_id`도 같은 번호를 씁니다.

| 센서 | BLE 이름 | 연구실 이름 | MAC | 설치 위치 |
| --- | --- | --- | --- | --- |
| 1 | `opensrc1` | sensor 07 | 88:A2:9E:9B:5F:09 | 도서관 뒤편 (진로창업본부 입구) |
| 2 | `opensrc2` | sensor 15 | 88:A2:9E:9B:5E:6A | 사회과학대 입구 |
| 3 | `opensrc3` | sensor 31 | B8:27:EB:D3:40:06 | 사회과학대 옆 이마트24 건너편 |
| 4 | `opensrc4` | sensor 32 | D8:3A:DD:79:8F:80 | 테니스장 앞 |
| 5 | `opensrc5` | sensor 33 | D8:3A:DD:C1:89:5B | 테니스장 건너편 |

- 연구실 이름은 연구실 공용 API(`/sensor/api/map`)에 표시되는 이름입니다. 센서 좌표도 이 API의 값으로 `sensors` 테이블에 들어 있습니다(`GET /api/sensors`).
- 패킷에는 센서ID가 들어 있지 않아서, 앱이 올릴 때는 MAC(없으면 BLE 이름)으로 센서를 구분합니다.
- 센서 3, 4(`opensrc3`, `opensrc4`)는 센서 문제로 값이 갱신되지 않거나 온도와 습도를 0으로 보냅니다. 연구실 서버에서도 최근 값이 없어서 해당 장소의 `latest_reading`은 `null`일 수 있습니다.
- 설치된 Pi 코드는 수정할 수 없습니다.

### 연구실 센서 (`kind`: `lab`)

- 연구실이 캠퍼스 곳곳에 설치한 센서입니다. 서버가 연구실 API를 가져올 때 **위치(위경도)가 있는 센서를 자동으로 등록**합니다. (예: 27종 중 오픈소스 5대를 뺀 22종)
- `sensor_id`는 **100 + 연구실 번호**입니다. (`sensor 18`은 118) 오픈소스 센서(1~5)와 겹치지 않습니다. `ble_name`과 `mac`은 없습니다.
- 온도와 CO2만 제공하고 습도는 없습니다. 센서가 계속 값을 올리는 것은 아니라서 갱신 중인 센서는 일부(예: 12종)뿐입니다.
- 오픈소스 센서와 마찬가지로 `GET /api/sensors`, `GET /api/sensors/status`에 나옵니다. `?kind=opensrc` 또는 `?kind=lab`으로 거를 수 있습니다.
- BLE 도착 판정은 앱이 오픈소스 센서(`opensrc1~5`)만 스캔하므로 연구실 센서는 온도를 빌려 쓰는 용도로만 쓰입니다.

## 실행

```bash
py -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
uvicorn app.main:app --reload
```

- API 문서(Swagger): http://127.0.0.1:8000/docs
- 최초 실행 시 `campus_tour.db`가 생성되고 센서 5대와 **실제 투어 장소 12곳, 코스 3개**(`app/tour_data.py`, #22)가 들어갑니다. 장소 12곳은 우리 센서가 설치된 4곳(도서관 뒤편, 사회과학대 입구, 이마트24 건너편, 테니스장)과 센서가 없어 가까운 센서 값을 빌려 쓰는 8곳입니다. 코스는 핵심 코스(덥거나 추울 때 추천하는 가장 짧은 코스), 정문 코스, 학생 생활 코스입니다. 연구실 연동을 끈 경우에만 센서마다 샘플 측정값이 들어갑니다. (테스트와 오프라인 개발용 샘플 장소는 `app/seed.py`에 따로 남아 있습니다.)
- 센서는 이미 만들어진 DB에도 자동으로 추가되지만, **장소와 코스는 DB가 비어 있을 때만** 들어갑니다. 예전 샘플이 들어 있는 `campus_tour.db`로 켜면 샘플이 그대로 보이니, 파일을 지우고 다시 켜세요. **표 구조가 바뀌어서**(장소가 센서를 여러 개 쓰도록 `spot_sensors` 표 추가, 센서에 `kind` 추가, 코스에 `is_core` 추가, 장소에 `has_card` 추가) 예전 `campus_tour.db`로 시작하면 안내 메시지가 나옵니다. 파일을 지우고 다시 실행하세요.
- DB 변경: 환경변수 `DATABASE_URL` (기본 `sqlite:///./campus_tour.db`)
- 서버를 켜면 연구실 서버에서 센서 온도를 1분마다 가져옵니다. 연구실 서버에 접속할 수 없는 곳(교외 등)에서 개발할 때는 `LAB_SYNC_ENABLED=0`으로 끄세요. 연동이 켜져 있으면 샘플 측정값은 넣지 않고(실제 값처럼 보이지 않게), 꺼져 있으면 센서마다 샘플 측정값 1건이 들어갑니다.
- 연동 상태는 `GET /api/lab-sync/status`로 확인합니다.
- **측정값 표(`readings`)의 구조가 바뀌어서**(일련번호 `seq`가 없어지고 공기질, RSSI 칸이 생김) 예전에 만든 `campus_tour.db`로 시작하면 안내 메시지가 나옵니다. 파일을 지우고 다시 실행하세요.

## 서버 열기 (노트북으로 시연할 때)

폰이나 다른 컴퓨터에서 접속하려면 서버를 **외부 접속을 받도록** 켜야 합니다. (`--host 0.0.0.0`) 위의 "실행"처럼 `uvicorn app.main:app --reload`만 쓰면 그 컴퓨터 안에서만 접속됩니다.

### 1. 서버 켜기

프로젝트 폴더(`app`, `README.md`가 있는 폴더)에서 실행합니다.

```powershell
copy .env.example .env          # 설정을 바꿀 것이 없으면 생략해도 됩니다
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --env-file .env
```

- 위 명령은 가상환경을 켜지 않고 그 안의 Python을 바로 실행하는 방식입니다. PowerShell에서 `.venv\Scripts\activate`를 그대로 입력하면 "`.venv` 모듈을 로드할 수 없다"는 오류가 나기 때문입니다. 가상환경을 켜고 싶으면 `.\.venv\Scripts\Activate.ps1`을 쓰세요. (명령 프롬프트 `cmd`에서는 `.venv\Scripts\activate`가 됩니다.)
- 터미널 경로가 프로젝트 폴더인지 확인하세요. 한 단계 바깥 폴더에서 실행하면 `.venv`를 찾지 못합니다.
- 서버가 "`campus_tour.db`를 지우라"는 안내를 내고 멈추면, 예전 구조의 DB 파일이 남아 있는 것입니다. 그 파일을 지우고 다시 켜세요. (센서 값은 연구실에서 다시 가져옵니다.)
- `.env.example`은 서버가 읽는 설정과 기본값의 목록입니다. `.env`로 복사해서 값을 바꿔 쓰고, `.env`는 저장소에 올리지 않습니다. `.env` 없이 켜려면 `--env-file .env`를 빼세요.
- 연구실 서버(`203.255.81.72`)에 접속할 수 없는 곳이면 `.env`에서 `LAB_SYNC_ENABLED=0`으로 끄세요.
- **처음 켜면 Windows 방화벽 창이 뜹니다.** "개인 네트워크" 접속을 **허용**해야 다른 기기가 접속할 수 있습니다.

### 2. 주소 확인과 접속 시험

1. 서버를 켠 컴퓨터에서 `ipconfig`를 실행해 **IPv4 주소**를 확인합니다. (예: `172.30.159.219`)
2. 같은 Wi-Fi에 연결한 폰의 브라우저에서 `http://IPv4주소:8000/health`를 엽니다. `{"status":"ok"}`가 보이면 접속이 되는 것입니다.
3. `http://IPv4주소:8000/docs`에서 API를 눌러 볼 수 있습니다.
4. 앱과 화면의 서버 주소를 `http://IPv4주소:8000`으로 설정합니다. (앱은 http 연결을 허용하도록 설정되어 있습니다)

### 3. 접속이 안 될 때

| 증상 | 확인할 것 |
| --- | --- |
| 폰 브라우저에서 아예 안 열림 | 서버를 켠 컴퓨터와 폰이 **같은 Wi-Fi**인지. 교내 Wi-Fi는 기기끼리의 통신을 막는 경우가 있습니다. 그러면 **폰 핫스팟**에 컴퓨터와 폰을 함께 연결해 보세요. |
| 컴퓨터에서는 열리는데 폰에서는 안 열림 | Windows 방화벽에서 Python의 **개인 네트워크** 접속이 허용되어 있는지. 서버를 `--host 0.0.0.0`으로 켰는지 |
| 어제는 됐는데 오늘은 안 됨 | Wi-Fi가 바뀌면 IPv4 주소도 바뀝니다. `ipconfig`로 다시 확인해서 앱의 주소를 고치세요. |
| 장소 카드에 온도가 없음 | `/api/lab-sync/status`에서 `last_error`를 확인하세요. 연구실 서버에 접속하지 못하면 여기에 원인이 나옵니다. |

### 4. 시연 전 점검 (발표 전에 한 번 해 보세요)

아래 주소는 모두 폰 브라우저에서 `http://IPv4주소:8000` 뒤에 붙여 엽니다. 노트북과 폰이 같은 Wi-Fi여야 합니다.

**노트북**
- [ ] **전원에 연결**되어 있고, **절전 모드와 화면 꺼짐으로 서버가 멈추지 않도록** 설정했다. (전원 옵션에서 "잠자기 안 함")
- [ ] 서버를 켜 둔 터미널 창을 닫지 않는다. (닫으면 서버가 꺼집니다)
- [ ] 발표장 Wi-Fi에서 `ipconfig`로 **IPv4 주소를 다시 확인**했다. (Wi-Fi가 바뀌면 달라집니다)

**폰에서 서버 확인**

| 열 주소 | 정상일 때 | 이상하면 |
| --- | --- | --- |
| `/health` | `{"status":"ok"}` | 같은 Wi-Fi인지, 방화벽, `--host 0.0.0.0`을 확인. 안 되면 폰 핫스팟으로 바꿈 |
| `/api/lab-sync/status` | `last_error`가 `null`이고 `last_success`가 최근. `stored`가 0보다 크면 센서 값이 저장되고 있음 | `last_error`에 원인이 나옴. 연구실 서버에 접속이 안 되는 곳이면 값이 비어 있음 |
| `/api/sensors/status` | 정상 센서는 `ok`. 값이 없는 센서(센서 3, 4)는 `no_data` 또는 `invalid`일 수 있음 | 센서 상태 표 참고 |
| `/api/spots` | 장소마다 온도가 있음. 한글이 깨지지 않음 | 온도가 `null`이면 그 장소와 가까운 센서 모두 값이 없는 것 |
| `/api/courses/recommend` | `condition`과 `reason` 문장이 나옴 | `unknown`이면 지금 쓸 수 있는 기온이 없는 것 (연구실 값 확인) |

- 값이 없는 센서에 연결된 장소(예: 이마트24 건너편)는 `value_source.is_on_site`가 `false`이고 `distance_m`가 나오면 가까운 센서 값을 빌려 쓰는 것이 정상입니다.

**앱 연결**
- [ ] 앱 제목을 길게 눌러 서버 주소 `http://IPv4주소:8000`을 입력했다. (비우면 앱에 들어 있는 샘플 데이터가 나옵니다)
- [ ] 홈에서 센서 점의 온도와 추천 코스 카드가 나온다. 장소 이름이 깨지지 않는다.
- [ ] 폰이 둘 이상이면 모든 폰의 서버 주소를 같은 값으로 맞췄다.

**발표 직전**
- [ ] 서버를 한 번 껐다 켜서 정상적으로 다시 뜨는지 확인했다.
- [ ] 연구실 서버가 응답하지 않아도 마지막 값을 보여주는 것을 알고 있다. (`last_success`가 오래되면 값이 오래된 것으로 표시됨)

## 실제 장소와 코스 넣기 (#22)

서버가 켜질 때 넣는 장소와 코스는 `app/tour_data.py`의 `SPOTS`와 `COURSES`에 있습니다. 지금 들어 있는 것은 홍유진 님이 #22에 정리한 실제 투어 12곳과 코스 3개입니다. 장소나 코스를 고칠 때는 이 파일을 고칩니다. (개발용 샘플은 `app/seed.py`에 따로 남아 있고, 테스트가 사용합니다.)

### 1. 장소 적기
`SPOTS`에 한 줄이 장소 하나입니다.

```python
# (이름, 영문, 소개, 센서 연결) 또는 (이름, 영문, 소개, 센서 연결, (위도, 경도))

# 센서가 설치된 장소: 센서 번호와 True. 좌표는 센서 좌표를 씁니다.
("도서관 뒤편", "Behind the Central Library", "중앙도서관 뒤편이에요.", [(1, True)]),

# 센서가 없는 장소: 센서 연결은 비우고 좌표를 적습니다. 200m 안의 가까운 센서 값을 빌려 씁니다.
("솔못", "Solmot Pond", "캠퍼스 중앙의 연못.", [], (36.6290, 127.4560)),
```

- 센서 번호는 `app/seed.py`의 `SENSORS`에 있는 1~5입니다.
- 좌표는 네이버, 카카오, 구글 지도에서 장소를 길게 누르거나 우클릭해서 복사합니다. 10~20m 오차면 충분합니다.
- 센서가 설치된 장소에서 좌표를 직접 적으면 센서 좌표 대신 그 값을 씁니다.
- 위도(36.6x)와 경도(127.4x)를 바꿔 적지 않게 주의하세요. 테스트가 잡아 줍니다.

### 2. 코스 적기
`COURSES`에 한 줄이 코스 하나입니다. 장소는 이름으로 찾는 `_n("솔못")`과 소요시간(분)으로 적습니다. (번호를 직접 세다가 틀리지 않게 하려는 것입니다.)

```python
("핵심 코스", "Core Course", "더울 때나 추울 때 추천하는 코스. 중앙도서관과 솔못만 둘러봐요.",
 [(_n("도서관 뒤편"), 5), (_n("솔못"), 13), (_n("사회과학대 입구"), 7)]),
```

- 소요시간은 "이전 지점에서 이동하는 시간 + 이 지점을 둘러보는 시간"의 합입니다. 이동 시간은 홍유진 님이 OSM 걷기 경로로 잰 값을 그대로 넣었고, 서버가 직선거리로 따로 계산하지 않습니다. **장소 순서를 바꾸면 이 숫자도 다시 정해야 합니다.**
- 환경 맞춤 코스 추천은 가장 짧은 코스와 가장 긴 코스 중에서 고르므로, **길이가 다른 코스가 2개 이상** 있어야 합니다.

### 3. 확인하고 반영하기
1. `pytest`를 실행합니다. 장소 번호 오류, 같은 장소 중복, 위도와 경도 뒤바뀜, 길이가 같은 코스 등을 `tests/test_seed_data.py`가, 실제 투어 데이터의 장소 수, 코스 시간, 도착 방식, 가까운 센서 빌리기를 `tests/test_tour_data.py`가 확인합니다. 장소나 코스를 바꾸면 `test_tour_data.py`의 기대값도 같이 고쳐야 합니다.
2. **시드는 DB가 비어 있을 때만 들어갑니다.** 이미 서버를 켠 적이 있으면 `campus_tour.db` 파일을 지우고 서버를 다시 켜야 새 장소와 코스가 반영됩니다. (센서 값은 연구실에서 다시 가져옵니다.)
3. 폰 브라우저에서 `/api/spots`와 `/api/courses`로 확인합니다.

### POST /api/readings 본문

앱이 BLE로 읽은 값을 우리 서버로 올립니다. (#9 에서 합의한 형식) 센서 온도는 연구실 서버에서도 가져오므로, 이 경로는 **습도와 공기질까지 담은 BLE 값을 직접 보낼 때**와 연구실 서버가 응답하지 않을 때의 보조 경로입니다.

```json
{
  "ble_name": "opensrc1",
  "mac": "88:A2:9E:9B:5F:09",
  "measured_at": 1790600000,
  "temperature": 24.1,
  "humidity": 48.0,
  "aqi": 2,
  "tvoc": 90,
  "eco2": 620,
  "rssi": -58
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `ble_name` | O | BLE 광고 이름 (`opensrc1~5`) |
| `mac` | | 센서 MAC. iOS는 알 수 없어서 생략할 수 있음. 소문자, 하이픈 표기도 같은 MAC으로 처리 |
| `measured_at` | O | 패킷의 측정 시각 (Unix 초, Pi 시계 기준) |
| `temperature` | O | ℃. 앱이 x100 정수를 실수로 풀어서 보냄 |
| `humidity` | O | %. 앱이 x100 정수를 실수로 풀어서 보냄 |
| `aqi`, `tvoc`, `eco2` | | 공기질. 화면에는 쓰지 않고 서버에 저장만 함 |
| `rssi` | | 폰이 받은 신호 세기(dBm). 저장만 함 |

**센서 찾기**
- `mac`이 있으면 MAC으로만 찾습니다. 등록된 MAC과 다르면 이름이 같아도 다른 기기(다른 팀 센서 등)일 수 있어서 거절합니다.
- `mac`이 없으면 `ble_name`으로 찾습니다.

**응답**

| 상태 | 의미 | 앱 동작 |
| --- | --- | --- |
| 201 `created` | 새로 저장됨 | 성공 |
| 200 `duplicate` | 같은 센서의 같은 `measured_at`이 이미 있음. 먼저 저장된 값을 유지 | 성공으로 처리 |
| 404 | 등록되지 않은 센서 | 재시도하지 않음 |
| 422 | 본문 형식 오류 (필수 필드 누락, MAC 형식, 공기질 범위 등) | 재시도하지 않음 |

- 측정 시각 기준 중복 제거라서, 앱이 재전송해도 안전합니다.
- **온도 -20~45도, 습도 0~100%를 벗어난 값은 거절하지 않고 저장**합니다. 다만 센서 오류값으로 보고 아래 응답의 최신값과 평균에서 제외합니다. (앱의 재전송 큐가 같은 요청을 반복하지 않도록 수업 서버와 같은 방식으로 맞춤)
- 센서가 온도와 습도를 0.0으로만 올려도 앱에서 거르지 않고 그대로 올려 주세요. 서버가 처리합니다.

### 장소 응답 (`/api/spots`, `/api/spots/{id}`, `/api/courses`의 `spot`)

```json
{
  "id": 4,
  "name": "테니스장",
  "has_card": false,
  "arrival": {
    "method": "ble_auto",
    "sensors": [
      { "sensor_id": 4, "ble_name": "opensrc4", "mac": "D8:3A:DD:79:8F:80", "location": "테니스장 앞" },
      { "sensor_id": 5, "ble_name": "opensrc5", "mac": "D8:3A:DD:C1:89:5B", "location": "테니스장 건너편" }
    ]
  },
  "latest_reading": {
    "sensor_id": 5, "measured_at": 1790600000,
    "temperature": 21.0, "humidity": null,
    "age_minutes": 1, "is_stale": false, "is_suspect": false
  },
  "recent_average": { "temperature": 21.0, "humidity": null, "count": 3, "window_minutes": 30 },
  "value_source": {
    "sensor_id": 5, "ble_name": "opensrc5", "lab_name": "sensor 33",
    "location": "테니스장 건너편", "is_on_site": true, "distance_m": 80
  }
}
```

**장소와 센서의 연결** (#2 합의)
- 장소 하나는 센서를 **여러 개** 쓸 수 있고(우선순위 순서), 센서 하나를 여러 장소가 쓸 수도 있습니다. 센서 4(앞)와 5(건너편)는 테니스장 한 장소로 묶었습니다.
- 온도는 연결된 센서를 우선순위 순서로 보고 **오래되지 않은 값이 있는 첫 센서**의 값을 씁니다. 전부 오래됐다면 가장 최근 값을 낸 센서의 값을 쓰고(`is_stale`이 `true`), 정상 값이 하나도 없으면 `latest_reading`이 `null`입니다. 예를 들어 센서 4가 죽어 있으면 테니스장은 센서 5의 값을 보여줍니다.
- **연결된 센서 중 오래되지 않은 값이 없으면, 가까운 센서의 값을 빌려 씁니다.** 장소 좌표를 기준으로 `MAX_BORROW_METERS`(기본 **200m**) 안에 있는 센서 중, 오래되지 않은 정상 값을 가진 **가장 가까운 센서**의 값을 씁니다. 오픈소스 센서와 연구실 센서 모두 대상입니다. 200m보다 먼 센서는 그 장소의 온도라고 보기 어려워 쓰지 않고, 조건에 맞는 센서가 없으면 `latest_reading`이 `null`입니다. 장소 좌표를 모르는 장소는 빌리지 못합니다. (센서가 설치된 장소의 좌표는 설치된 센서의 좌표입니다)
- 빌려 온 값은 `value_source.is_on_site`가 `false`입니다. 이웃 센서가 오래된 값만 가지고 있으면 현재 온도를 대신하지 않습니다.

**`arrival`: 도착을 어떻게 체크하는가**
- `ble_auto`: 장소에 설치된 센서가 있어 BLE로 자동 판정합니다(수동 "도착" 버튼은 보조). `sensors`에 도착 판정에 쓰는 센서(BLE 이름, MAC)가 들어 있어서, 앱이 스캔한 센서가 이 목록에 있으면 이 장소에 도착한 것입니다.
- `manual`: 센서가 없는 장소입니다. 방문객이 "도착" 버튼으로 체크하고 `sensors`는 빈 목록입니다.

**`value_source`: 온도가 어느 센서의 값인가**
- `is_on_site`가 `true`면 이 장소에 설치된 센서의 값이고, `false`면 센서가 없는 장소가 **가까운 센서 값을 빌려 쓴 것**입니다. 화면에는 `location`을 이용해 "사회과학대 입구 센서 기준"처럼 출처를 표시합니다.
- `distance_m`은 장소와 센서 사이의 거리(m)입니다. "약 56m 떨어진 센서 기준"처럼 표시할 수 있습니다. 장소나 센서의 좌표를 모르면 `null`입니다.
- 연구실 센서의 값이면 `ble_name`이 `null`이고 `lab_name`(예: `sensor 18`)이 있습니다. `location`은 "연구실 센서 18번"처럼 나옵니다.
- 측정값이 없으면 `null`입니다.

**필드 변경**: 장소의 `sensor_id`, `ble_name`은 없어졌고 `arrival.sensors`로 대체되었습니다.

**환경값 설명**

- `is_stale`: 측정 후 `STALE_MINUTES`(기본 30분) 이상 지났으면 `true`. 센서 전원이 꺼진 경우에 "오래된 값"으로 표시하는 용도입니다.
- `is_suspect`: 최신 측정값과 온도, 습도가 같은 값이 `FIXED_VALUE_MIN_COUNT`(기본 5)개 이상 연속이고, 그 구간이 `FIXED_VALUE_MINUTES`(기본 10분) 이상 이어지면 `true`. 센서가 멈춘 것으로 의심하는 표시이고, **값은 버리지 않고 그대로 저장**합니다. 이때 `recent_average`는 `null`입니다. 센서가 1초 간격으로 값을 내면 몇 초 동안 같은 값이 나올 수 있어서 시간 조건을 함께 봅니다.
- `has_card`: 이 장소에 도착하면 앱이 카드를 띄우는지(#37) 나타냅니다. 핵심 코스의 장소(도서관 뒤편, 솔못, 사회과학대 입구)와 개신문화관, 박물관, 야외공연장이 `true`입니다.
- `recent_average`: 최근 `AVG_WINDOW_MINUTES`(기본 30분) 안의 측정값 평균. 측정값이 없으면 `null`입니다.
- `latest_reading`, `recent_average`는 연결된 센서가 없거나 정상 측정값이 없으면 `null`입니다.
- **`humidity`는 `null`일 수 있습니다.** 연구실 API로 가져온 값에는 습도가 없습니다. 화면에는 온도만 표시하고 습도는 쓰지 않는 방침입니다. `temperature`는 연구실 값이면 정수(소수점 버림)이고, BLE로 올린 값이면 소수점이 있습니다.
- `is_suspect`(고정값 의심)는 BLE로 받은 값에만 적용합니다. 연구실 값은 정수 온도라서 같은 값이 계속 나오는 것이 정상입니다.
- **센서 오류값은 최신값, 최근 평균, 고정값 판정에서 제외**합니다. 값은 버리지 않고 저장합니다. 오류값은 아래 두 경우입니다.
  - 온도 -20~45도, 습도 0~100%를 벗어난 값
  - 온도와 습도가 **모두 0.0**인 값 (연결 불량 등으로 센서가 0만 올려 보내는 경우). 온도 0.0도는 겨울에 실제로 나올 수 있어서 습도가 0이 아니면 정상 값입니다.

### GET /api/sensors/status

센서마다 한 항목씩, `sensor_id` 순서로 내려줍니다. 등록된 센서, 장소에 연결된 센서, 측정값을 보낸 적 있는 센서가 모두 나옵니다. 등록되지 않은 센서는 `ble_name`, `mac`, `location`이 `null`입니다.

```json
[
  {
    "sensor_id": 1,
    "ble_name": "opensrc1",
    "mac": "88:A2:9E:9B:5F:09",
    "location": "도서관 뒤편 (진로창업본부 입구)",
    "spot_names": ["도서관 뒤편"],
    "status": "ok",
    "latest_reading": { "temperature": 23.5, "humidity": 48.2, "age_minutes": 3, "is_stale": false, "is_suspect": false },
    "last_received_at": 1731000010
  }
]
```

| `status` | 의미 |
| --- | --- |
| `ok` | 최근 값이 들어오고 있음 |
| `stale` | 마지막 측정이 오래됨 (센서 전원 꺼짐, 근처에 앱 사용자가 없음 등) |
| `suspect` | 최근 값이 계속 같음 (센서 멈춤 의심) |
| `invalid` | 측정값은 오지만 전부 오류값(범위 밖이거나 온도와 습도가 모두 0.0). 센서 점검 필요 |
| `no_data` | 등록되었거나 장소에 연결되어 있지만 측정값을 받은 적 없음 |

- 우선순위는 `no_data` > `invalid` > `stale` > `suspect` > `ok`입니다.
- `last_received_at`은 서버가 값을 받은 시각입니다. `latest_reading.measured_at`과 크게 다르면 Pi 시계가 틀렸을 가능성이 있습니다.
- 연구실 API 값은 센서가 직접 올리는 것이라 계속 갱신되지만, 앱이 BLE로 올리는 값(습도 포함)은 폰이 근처를 지나갈 때만 들어옵니다.

### GET /api/courses/recommend

지금 기온에 맞는 코스를 골라 줍니다. 앱은 이 응답의 `recommended_course_id`와 `reason`을 그대로 보여주면 됩니다.

- **모든 코스의 장소를 합쳐서**(한 장소는 한 번만) **현재 기온 평균**으로 판단합니다. 오래된 값(`is_stale`)은 쓰지 않습니다.
- 센서가 없는 장소가 가까운 센서 값을 빌려 쓰면 여러 장소가 같은 센서 값을 갖게 되므로, **같은 센서의 값은 평균에 한 번만** 넣습니다. (`sample_count`는 이렇게 센 값의 수입니다.)
- `courses`의 `average_temperature`는 그 코스의 장소만으로 같은 방식으로 구한 평균입니다.
- `COLD_MAX_CELSIUS`(기본 5℃) 이하면 `cold`, `HOT_MIN_CELSIUS`(기본 27℃) 이상이면 `hot` → **가장 짧은 코스**
- 그 사이면 `comfortable` → **가장 긴 코스**
- 기온을 아는 장소가 없으면 `unknown` → 기본 코스(가장 긴 코스)
- 길이가 같으면 번호가 작은 코스입니다.

```json
{
  "condition": "cold",
  "temperature": 3.5,
  "sample_count": 4,
  "thresholds": {"cold_max": 5, "hot_min": 27},
  "recommended_course_id": 1,
  "recommended_course_name": "짧은 코스",
  "reason": "기온 3.5도로 추워서 가장 짧은 코스(짧은 코스)를 추천합니다.",
  "courses": [
    {"id": 1, "name": "짧은 코스", "total_minutes": 25, "average_temperature": 3.5, "recommended": true},
    {"id": 2, "name": "기본 코스", "total_minutes": 45, "average_temperature": 3.5, "recommended": false}
  ]
}
```
